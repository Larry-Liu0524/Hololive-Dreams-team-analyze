# Hololive Dreams 隊伍最佳化分析器

一個非官方的粉絲製作工具，幫《hololive Dreams》玩家評估隊伍組成、找出主動技/SP技能設計最好的隊伍搭配。單一 HTML 檔案、不需安裝，開啟即可使用，所有資料存在瀏覽器本機（`localStorage`），不會上傳到任何伺服器。

🔗 **線上使用**：[larry-liu0524.github.io/hololive_dreams_team_builder.html](https://larry-liu0524.github.io/hololive_dreams_team_builder.html)

> 非官方粉絲網站，與 COVER Corp. / QualiArts 無關聯。

---

## 這個工具在做什麼

市面上其他 hololive Dreams 攻略/編隊網站（例如 horodori.com、holodori.best）大多只計算「基礎數值＋隊長服裝加成」，主動技/SP技能通常只列出條件是否成立，沒有真的去模擬「這些技能在整首歌的時間軸上，實際上重疊了多少、留白了多少」。

這個工具的核心差異化，就是專門解決這個問題：把每張卡的主動技依 Interval/Duration 展開成整首歌的時間軸事件，實際模擬 5 人＋隊長的技能觸發節奏，量化「主動技覆蓋率」跟「加成強度」；被動技能也不是單純看條件PASS/FAIL，而是模擬「隊伍站位順序」決定誰實際吃得到誰的加成。並且反過來用這個模型**搜尋**最佳隊伍組合與最佳「主動技能發動頻率天賦」配置。

## 分頁功能一覽

| 分頁 | 功能 |
|---|---|
| ① 我的角色庫 | 勾選持有角色、設定開花等級（0-5），支援中/英文搜尋 |
| ② 隊伍分析與最佳化 | 唯一的搜尋/分析入口：指定隊長（僅列持有角色）、候選池選「持有角色」或「資料庫全部卡片」、可手動鎖定隊員。搜尋採分層優先邏輯（隊長條件PASS＞被動全員滿足＞其他分數）＋完整窮舉，保證找到候選範圍內符合最高優先層級的全域最佳解（持有角色範圍通常幾分鐘內跑完；全資料庫範圍視分層篩選後的候選數量，可能數分鐘到數小時，支援即時進度條/取消）；也可以直接「分析目前手動隊伍」快速幫排好的固定隊伍打分數 |
| ③ 抽卡 ROI 推薦 | 沿用②最後一次的分析結果當基準，依當時候選池設定分兩種模式：持有角色→推薦該抽哪張卡；全部卡片→抽卡優先順序 |
| ④ 卡片／歌曲查詢 | 瀏覽/搜尋卡片與歌曲資料庫、已儲存的隊伍快照 |
| ⑤ 資料庫編輯 | 卡片資料的新增/編輯/刪除/JSON 匯入匯出 |
| ⑥ 方法論／資料來源 | 評分公式、各項假設與已知限制的完整說明 |

> ②的搜尋功能原本拆成「②依持有角色」「③指定隊長找全資料庫」「⑧完整窮舉」三個分頁，前兩者走的是貪婪法＋局部優化的近似解、跑得快但不保證最優。考量到這款遊戲養角色要投入大量資源與時間、沒辦法說換隊就換隊，近似解的價值有限，已把貪婪法整套移除、三個分頁合併成一個，統一改用完整窮舉。

## 核心評分邏輯

Overall Score = 隊長服裝 30% ＋ 隊員被動 25% ＋ 時間軸覆蓋率（主動技）20% ＋ 覆蓋效率（主動技，加成強度加權）10%，原始權重總和 85%，已正規化為 100%。SP 技能出場順序與 Connect 數值不列入加權，僅供參考。

**主動技能發動頻率天賦**（0/4/8/12%，屬於每位 Holomem 的天賦盤節點）：效果是把該角色的 Active Interval 縮短為 `interval/(1+加成%)`。依實測驗證（同一張卡分別測 0%/8%/12%，用碼表對照理論值），觸發序列是「整條從 t=0 開始、直接套用縮短後的 interval 重算」——這代表頻率天賦會讓觸發時間點整體「相位位移」，如果新窗口撞進隊友既有的觸發時間，反而會變成純粹的重疊浪費，不是「點越高分數越高」。②的搜尋功能會對每個候選隊伍窮舉頻率天賦排列組合，找出讓 Timeline+Coverage 分數最高的配置。

**覆蓋效率（10%）**：已確認遊戲規則——同類型 Active「Score Up」效果不會疊加，多個主動技同時生效時只採計當下最高的 %數，較低的那個被浪費掉。這裡把「每個時間點實際生效的最高 %數」對整首歌積分後取平均，得到「全曲平均有效加成%」，計分時封頂 100 分，但畫面上會額外顯示未封頂的原始數字。

**隊員被動（25%）**：已改成真正的「受益者模擬」，不再只看「這張卡自己的條件有沒有觸發」。已確認遊戲規則：被動條件寫「N人」，若隊伍裡符合條件的人數超過N，只有依隊伍站位順序排在最前面的N人吃得到加成，其餘符合條件但排序較後面的人吃不到；「自身限定」型被動則不受排序規則影響。分析結果的「逐位隊員條件檢查」表格會拆成「被動條件」（卡片自己有沒有觸發）跟「被動加成」（這位隊員自己實際上有沒有吃到、吃到誰的、或吃不到的原因）兩個獨立欄位。

**SP 技能時機**：實測發現 SP 技能第一次觸發的時間點依歌曲不同而不同（同一張卡在不同歌曲測到 15 秒／23 秒兩種結果），且這個時間點無法透過選卡或天賦點數改變，公開資料裡也沒有說明這個機制。因此 SP 技能完全不參與覆蓋率／空檔／加成強度的計算，時間軸圖表上仍會畫出 SP 區塊，但橫向位置僅供參考；SP 技能真正確定的資訊是站位順序，不是時間點。

**主動技的條件式加成**（約49%的卡片有這個機制）：不少卡片除了固定 base value，還有「條件成立時才吃得到」的更高 %數（例如「Pure屬性2人以上時 +120%」）。屬性型用隊伍當下實際人數判斷；生命值型／連段型屬於動態遊戲狀態，本工具沒有逐拍模擬，採樂觀假設「一輪打得漂亮的話會達成」，跟既有「Active 100%發動」假設同一立場——這部分的分數是上限估計，不是保證值。

**②搜尋時的分層優先邏輯**：Overall Score 加權總分只用來在「同一優先層級內」比較候選隊伍。②的搜尋會先依兩個硬性條件分層——隊長服裝條件有沒有 PASS，優先於隊員被動是不是全員都吃到加成，優先於其他分數（強度/覆蓋率）——只有落在最高優先層級的候選才會用加權總分決定最終排名。這代表時間軸再完美，也贏不過「隊長條件 PASS ＋ 被動全員滿足」的隊伍，是保證的結果而非機率上的傾向。這個分層同時帶來明顯效能提升：先用不含頻率窮舉的便宜評分（約1毫秒/組）篩過所有候選，只有最高優先層級的候選才需要真的跑完整頻率天賦窮舉（約20~110毫秒/組）——實測下通常能篩掉八成以上不需要的候選。

## 已知限制

- Active 技能實際上是「每 interval 秒判定一次、依機率發動」，本工具假設每次判定都必定觸發（100%）——這是刻意的簡化，因為工具設計目標是「衝排行榜」場景（刷到技能都順利發動的那一輪才算數）
- 沒有歌曲 BPM／逐秒 note 密度資料，覆蓋率只衡量技能生效的**時間長度**，不代表換算到分數的實際效益
- SP 技能第一次觸發的時間點依歌曲不同而不同，且無法被隊伍決策影響，公開資料也沒有解釋這個機制——SP 完全不參與任何計分，時間軸上的位置僅供參考
- 被動技能的「スコアサポート效果」跟「單一屬性/全能力」之間的強度換算比例，目前沿用跟隊長服裝一致的假設（不特別加權），這不是獨立驗證過的結論
- 天賦盤的紅（隊長限定）／黃（不入隊也發動）／藍（入隊限定）三色節點數值目前沒有公開資料表，尚未納入模型——目前只有「頻率天賦」這一種節點被建模；但已找到遊戲原始資料庫的公開鏡像（HolodoriDB GitHub組織），內含`SkillTreeNode`/`SkillTreePoint`等天賦盤節點資料，之後有需要可以直接解析補完整
- 被動受益者模擬與主動技條件式加成讓單次評分的運算成本變高，但②的搜尋已改用分層篩選（先用便宜評分篩掉不符合最高優先層級的候選，只對篩選後的候選跑昂貴的頻率天賦窮舉），實測下通常能篩掉八成以上候選，整體耗時比純暴力法快不少
- 主動技條件式加成中的生命值／連段門檻，採樂觀假設「一定會達成」，可能高估部分卡片的實際貢獻
- ROI（③）分頁的分析依②當時的候選池設定分流，還沒有獨立的頻率天賦最佳化選項

## 技術架構

單一 `hololive_dreams_team_builder.html` 檔案，純 Vanilla JS + inline CSS，無框架、無建置流程，直接開啟即可用。資料持久化全部透過瀏覽器 `localStorage`（持有角色、開花等級、卡片資料庫、隊伍快照等），不經過任何後端。
